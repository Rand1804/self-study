# Claude Code 使用技巧精华

> 适合已经安装好 Claude Code、希望尽快提高使用效率的人。这里重点不是安装，而是“怎么用得更稳、更快、更省心”。

## 1. 先学会一个高价值工作流：探索 → 计划 → 实施 → 验证

Claude Code 最有价值的用法，不是“直接让它改代码”，而是让它按工程化流程工作。

推荐你经常这样下指令：

- 先探索相关代码和调用链
- 给出一个简短实现方案
- 我确认后再修改
- 修改后运行指定测试或命令验证

例如：

```text
先阅读相关文件，告诉我这个模块的输入输出和调用链；
然后给出最小改动方案；
等我确认后再改；
最后运行对应测试验证。
```

这比一句“帮我改一下”稳定很多，特别适合中大型代码库。

## 2. 一开始就把“验证标准”说清楚

这是 Claude Code 最关键的使用技巧。

不要只说：

```text
修一下这个 bug
```

更好的说法是：

```text
先写一个能复现问题的测试；
修复后跑这个测试；
如果有相关回归测试也一起跑。
```

或者：

```text
修改后请执行 `make test`；
成功标准是 xxx 日志出现 / 某个命令返回 0 / 某个页面显示正常。
```

经验上，**你给 Claude 的“成功判据”越具体，返工越少**。

## 3. 复杂任务优先用 Plan Mode，而不是直接开改

当任务有以下特点时，优先先规划：

- 你自己也还没完全想清楚范围
- 可能会改多个文件
- 有多种实现路径
- 你对这块代码还不熟

Plan Mode 的好处是：

- Claude 先读代码、给方案
- 不会直接改文件
- 你可以先纠正方向，再让它实施

这特别适合：

- 重构
- 新功能
- 跨模块问题排查
- 需要权衡方案的任务

## 4. 提示词尽量包含“边界条件”和“约束”

Claude Code 很强，但它不会自动知道你的隐含要求。

建议把这些信息尽量前置：

- 只允许最小改动
- 不要重构无关代码
- 保持现有风格
- 不要新增抽象
- 不要改公共接口
- 只修 bug，不做顺手优化

例如：

```text
只做最小改动修复这个问题；
不要改接口；
不要顺手重构；
保持当前代码风格；
改完后跑单测。
```

这类约束对资深工程师尤其有用，因为你通常更在意“改动是否可控”。

## 5. 善用 `@文件` 和 `@目录`，减少无效搜索

如果你已经知道大概位置，不要让 Claude 全仓库盲找。

可直接在提示里带上：

- `@某个文件`
- `@某个目录`

这样做的好处：

- 上下文更聚焦
- 响应更快
- 更不容易读偏
- 更省上下文窗口

适合你这种技术笔记仓库，也适合大型嵌入式工程仓库。

## 6. 会话上下文是稀缺资源，要主动管理

Claude Code 不是“聊得越久越好”。

要养成这几个习惯：

- 用 `/clear` 清掉无关任务上下文
- 用 `/compact` 压缩当前会话
- 用 `/context` 看上下文占用情况
- 无关的新问题，不要硬接在同一个长会话里

常见误区：

- 一个会话里同时聊多个完全不相关的问题
- 让 Claude 长时间做“无范围调查”
- 把大量一次性要求都堆进对话里

如果你发现它开始“跑偏”或“反复纠正还是不对”，通常重新开一个更清晰的新会话更快。

## 7. 把长期规则放进 `CLAUDE.md`，不要只靠临时聊天

如果你有稳定偏好，比如：

- 总是先给计划再改
- 只做最小改动
- 必须跑测试
- 不要自动提交 git commit
- UI 变更必须先验证

这类规则应该写进 `CLAUDE.md`，而不是每次重新说。

好处：

- 降低重复沟通成本
- 多次会话保持一致
- 减少上下文漂移

但也不要把 `CLAUDE.md` 写得太臃肿。**规则少而硬，比多而散更有效。**

## 8. Slash Commands 先掌握这些高频项

建议优先熟悉下面这些命令：

- `/plan`：先做方案，不直接修改
- `/permissions`：查看和调整权限策略
- `/context`：查看上下文使用情况
- `/compact`：压缩上下文
- `/clear`：清空当前任务上下文
- `/diff`：看改动差异
- `/review`：做代码审查
- `/security-review`：做安全审查
- `/doctor`：排查 Claude Code 自身问题
- `/agents`：查看/管理子代理
- `/hooks`：查看/配置 hooks
- `/init`：初始化项目说明

如果你还在入门阶段，优先掌握 `/plan`、`/context`、`/compact`、`/clear`、`/diff`、`/doctor` 就已经很够用了。

## 9. 子代理（subagents）适合“支线任务”

当一个任务里面有明显支线时，子代理很有价值。

典型场景：

- 让一个子代理专门搜索代码
- 让一个子代理做安全审查
- 让一个子代理检查某段实现是否有边界漏洞
- 让一个子代理看文档/日志，再只返回结论

优势：

- 主会话不被大量搜索结果污染
- 支线问题可以并行处理
- 最后只拿摘要，主线更清爽

简单理解：

- **同一任务内的并行调查**：优先考虑 subagents
- **完全不同方向的独立开发任务**：优先考虑 worktree

## 10. Worktree 适合并行开发多个独立任务

如果你同时想做两件独立事情，比如：

- 一边修 bug
- 一边尝试一个新特性

这时更适合开 worktree，而不是把所有事塞进一个工作区。

好处：

- 各自独立分支
- 互不污染
- 适合并行实验
- 更利于审查和回退

**subagent 解决的是“分析并行”，worktree 解决的是“开发并行”。**

## 11. 权限模式要理解，不要一味图快

Claude Code 的权限控制其实很重要。

你至少要理解几种常见模式的差异：

- 默认模式：更谨慎
- plan 模式：只读规划
- auto：更自动，但要清楚风险
- bypassPermissions：高风险，只适合隔离环境

实战建议：

- 日常开发先用保守模式
- 高频、低风险命令可以逐步放开
- 涉及外部系统、部署、删除、覆盖时要特别谨慎

对于你这种工程背景，**“可控”通常比“全自动”更重要**。

## 12. 为常用命令做权限白名单，减少重复批准

如果你经常要让 Claude 执行这些低风险命令：

- 单元测试
- lint
- 格式化
- 只读搜索

可以通过 `/permissions` 逐步放开，减少每次重复确认。

这样既保留安全边界，又能提升效率。

## 13. 检查点（checkpoints）很有用，但别误解它的边界

Claude Code 会在改文件前做检查点，这意味着：

- 可以撤销它做过的文件修改
- 在改坏时更容易回退

但注意：**检查点不等于所有操作都可撤销。**

以下动作通常不在“轻松回退”范围内：

- 数据库变更
- 远程 API 调用
- deploy
- 对外发消息
- 修改共享环境

所以凡是“超出本地文件编辑”的操作，仍然要谨慎。

## 14. 养成“先让它复现，再让它修”的习惯

对于 bug，推荐固定套路：

1. 先定位相关代码
2. 先写失败测试 / 复现步骤
3. 再修复
4. 跑最相关测试
5. 必要时补回归验证

这比直接让它“猜着修”靠谱很多。

## 15. 多用 Claude 调研，但别让它无限制发散

错误示范：

```text
帮我研究一下这个仓库
```

更好的说法：

```text
请只看 `drivers/` 和 `platform/`；
帮我说明 UART 初始化链路；
输出关键函数、调用顺序，以及修改波特率应该改哪里。
```

原则是：

- 指定范围
- 指定输出格式
- 指定你要的结论

这样最适合复杂的嵌入式代码仓库。

## 16. Claude Code 不只会“写代码”，更适合做这些事

高价值用途包括：

- 快速理解陌生模块
- 画出调用链 / 数据流
- 总结某个目录职责
- 找配置入口
- 比较两个实现差异
- 先做 code review
- 先做安全审查
- 批量整理文档

对资深工程师来说，它更像一个**高带宽工程助手**，不只是代码生成器。

## 17. 脚本化场景可以用 `claude -p`

如果以后你想把 Claude Code 用到：

- shell 脚本
- 批处理
- CI
- hooks

可以关注 `claude -p` 这种非交互式用法。

适合把固定流程自动化，例如：

- 审查指定 diff
- 总结日志
- 检查某个目录是否有风险改动
- 生成格式统一的说明

## 18. 当 Claude 表现异常时，先用 `/doctor`

如果遇到这些问题：

- 搜索不准
- 文件引用异常
- MCP / hooks / 配置怪异
- 行为和预期不一致

优先跑 `/doctor`，通常比猜原因快。

## 19. 最常见的几个误区

### 误区 1：任务描述过于模糊
不是 Claude 不行，而是约束不够。

### 误区 2：没有验证标准
没有测试、没有命令、没有成功条件，输出就容易“像对其实没验”。

### 误区 3：一个会话塞太多主题
上下文污染后，质量会下降。

### 误区 4：复杂任务直接开改
先计划通常更省时间。

### 误区 5：让它做无限范围调研
会读很多无关内容，浪费上下文。

### 误区 6：把所有长期偏好都放聊天里
应该沉淀到 `CLAUDE.md` 或技能中。

## 20. 一个适合日常使用的提示模板

你可以直接套这个模板：

```text
先阅读 @相关文件 或 @相关目录，
告诉我当前实现的关键调用链和修改点；
然后给出最小改动方案；
等我确认后再实施；
实施后运行 [测试命令/验证命令]；
不要改无关代码，不要额外重构。
```

如果是 bug：

```text
先复现问题，优先写失败测试；
再做最小修复；
修复后运行相关测试；
最后告诉我改了哪些文件，以及为什么这样改。
```

## 21. 给你的个人建议（结合嵌入式工程背景）

你本身是资深嵌入式软件工程师，使用 Claude Code 时最值得强化的，不是“让它多自动”，而是：

- 让它先帮你快速理解陌生代码
- 让它输出调用链和边界条件
- 让它按“最小改动 + 可验证”的方式工作
- 让它承担文档整理、代码审查、影响面分析这类高回报任务

对嵌入式/底层工程尤其有效的提示方式是：

- 明确模块边界
- 明确寄存器/驱动/协议栈层级
- 明确时序或状态机约束
- 明确验证手段（日志、单测、仿真、硬件现象）

---

## 一句话总结

**Claude Code 用得好的核心，不是“让它直接写”，而是“让它在明确约束下，按工程流程探索、实施并验证”。**
